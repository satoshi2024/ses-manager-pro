## 3. Task B: 一覧エクスポートのメモリ上限化

### 3.1 現状の問題

`/api/engineers/export` と `/api/contracts/export` は、次の3段階で全件をメモリへ保持する。

1. `selectList` / `service.list` が全エンティティを `List` 化する。
2. 契約はさらに全件を `ContractExportDto` へ変換する。
3. `SXSSFWorkbook` を使用していても、最後に `ByteArrayOutputStream` と `ResponseEntity<byte[]>` で完成ファイル全体をヒープへ載せる。

`SXSSFWorkbook` は行データを一時ファイルへ退避するだけであり、現在の `byte[]` 応答では最終成果物のメモリ保持を解消できていない。また、`/api/engineers/export-csv` と `/api/projects/export-csv` も全件 `List` + `StringBuilder` + `byte[]` であり、同系統の問題を持つ。

### 3.2 採用する方式

#### 必須

- DBは `id DESC` の**キーページング**で分割取得する。`OFFSET` は後半ほど遅くなるため使用しない。
- 1バッチは設定化する。推奨既定値は500、許容範囲は100〜2000とする。
- Excelは `SXSSFWorkbook` を維持しつつ、完成内容を `HttpServletResponse.getOutputStream()` へ直接書く。`ByteArrayOutputStream` と `ResponseEntity<byte[]>` を一覧出力経路から除去する。
- CSVはUTF-8 BOMとヘッダを書いた後、各バッチを `BufferedWriter` へ直接書く。全件 `StringBuilder` を作らない。
- 出力中に保持する業務行は原則1バッチ分だけにする。契約の要員名・案件名・顧客名解決もバッチ単位で一括取得し、N+1にしない。
- 既存の検索条件、並び順、列順、数式インジェクション対策、データスコープを完全に維持する。
- `SXSSFWorkbook#dispose()` は成功・失敗に関係なく必ず実行する。
- 1プロセス当たりの同時エクスポート数を設定で制限する。推奨既定値は2。許容量を超えた要求は処理開始前に429を返し、待機キューを無制限に作らない。
- 現在の `GlobalExceptionHandler#toHttpStatus` は429を未定義のため、そのまま `BusinessException(429, ...)` を投げるとHTTP 500になる。429のHTTPマッピングと回帰テストを追加する。
- 上限超過・同時実行超過のメッセージは日本語を直書きせず、4バンドルへ同じキーを追加する。

#### 対象エンドポイント

- `/api/engineers/export`
- `/api/contracts/export`
- `/api/engineers/export-csv`
- `/api/projects/export-csv`

月次売上レポートは12行固定のため対象外とする。単票のスキルシートや請求書PDFも対象外とする。

#### 明示的に採用しない方式

- `ResponseEntity<StreamingResponseBody>` へ型だけ変更し、内部で全件 `List` / `byte[]` を作る方式。
- `LIMIT/OFFSET` による分割。
- 件数超過時の黙った切り捨て。
- Hikariのプールサイズ増加だけで問題を回避する方式。
- このタスクで非同期ジョブ管理、S3等の外部ストレージ、汎用帳票基盤まで導入すること。

### 3.3 行数上限についての判断

ストリーミング化はOOMを抑えるが、数百万行の同期ダウンロードがTomcatスレッド、DB、ローカル一時領域を長時間占有する問題までは解消しない。そのため `app.export.max-rows` を設ける。

- 推奨既定値: 50,000行
- 上限超過時: ダウンロード開始前に400を返し、「検索条件を絞り込んでください」と明示する
- 0以下を無制限の意味にしない。誤設定は起動時または設定読込時に安全な既定値へ正規化する
- 件数を黙って50,000行で打ち切らない

50,000行を超える出力が実業務要件として確認された場合だけ、別タスクとして「非同期エクスポートジョブ + 期限付きファイル保存 + 完了通知」を設計する。同期APIの上限を単純に引き上げない。

### 3.4 データスコープ上の注意

現在の `DataScopeService` はID集合をメモリへ作り `IN (...)` へ渡す方式で、インターフェースコメントも数百件規模を前提としている。本タスクでは既存の認可結果を絶対に弱めない。

- まず既存の `allowedEngineerIds()` / `allowedContractIds()` と同じ母集団になることを回帰テストで固定する。
- 50,000行級で巨大なID集合が実測上のボトルネックになった場合は、Task Cの後続として `EXISTS` / JOIN によるSQL側スコープへ移す。
- エクスポートだけ独自の簡略化した認可条件を実装しない。

### 3.5 受入条件

1. 対象4エンドポイントの一覧出力経路に全件 `list()`、全件DTOリスト、完成ファイル `byte[]` が残っていない。
2. 1,201件のテストデータをバッチサイズ500で出力したとき、DB取得が500/500/201の3バッチになり、重複・欠落・順序逆転がない。
3. 既存の検索条件とデータスコープ適用時でも重複・欠落がない。
4. Excel/CSVを実際に再読込し、ヘッダ、先頭行、境界行（500/501）、最終行、総行数が一致する。
5. 文字列先頭 `=`, `+`, `-`, `@`, タブの数式インジェクション対策が維持される。
6. 3件目の同時エクスポートは処理開始前に429となり、先行2件の終了後は再実行できる。
7. 50,001件はファイル送信開始前にエラーとなり、50,000件は出力できる。黙った切り捨てがない。
8. 例外時にも同時実行枠とSXSSF一時ファイルが解放される。
9. 全テスト成功。可能なら固定ヒープ（例: `-Xmx256m`）で大件数出力を行い、OOMしないことを確認する。
10. 429がHTTP 500へ変換されず、レスポンス本文の `ApiResult.code` も429になる。

## 4. Task C: 数十人超の同時接続への対応

### 4.1 結論

この項目は単発の実装タスクにしない。最初は **Task C0（容量基準と実測）だけ**を他AIへ依頼し、そのレポートをレビューしてからC1以降を決める。

「ログイン中ユーザー100人」と「同時に重いAPIを100本実行」は別物である。最低限、以下を入力として確定する。

- ログインセッション総数
- ピーク時の同時アクティブリクエスト数 / req/s
- 代表データ量（要員、契約、実績、請求、監査ログ）
- 代表操作の比率
- p95応答時間とエラー率のSLO
- 単一インスタンス継続か、複数インスタンス/ローリング更新が必要か
- MySQLのCPUコア、メモリ、最大接続数、アプリJVMヒープ

未確定時の**計測用仮置き**は次のとおりとする。これは製品保証値ではない。

- 100ログインセッション
- 50同時アクティブユーザー
- 30分継続
- 読取95% / 更新5%。エクスポートは通常シナリオと分けて2並行で測る
- 通常API p95 1秒未満、エラー率1%未満
- 実データ相当以上のMySQLデータセットを使用し、H2結果を容量判断に使わない

### 4.2 Task C0: ベースライン計測

#### 実施内容

1. ログインとCSRF Cookie/Header複写を含む再実行可能な負荷試験を用意する。
2. 代表シナリオを、一覧/詳細、ダッシュボード、通知、更新系、エクスポートに分ける。
3. p50/p95/p99、req/s、HTTPエラー、Hikari active/idle/pending、Tomcat busy thread、MySQL CPU/接続/slow query、JVM heap/GCを同じ時刻軸で採取する。
4. 20→50→100の段階負荷で、最初にSLOを外す箇所を特定する。
5. 計測結果と再現手順を `.kiro/audits/` に保存する。

#### 禁止事項

- 計測前に `DB_POOL_SIZE` や `TOMCAT_MAX_THREADS` を増やす。
- H2の負荷試験結果から本番容量を推定する。
- ダッシュボードが過去に重かったという理由だけで、現在の全ボトルネックを推測する。
- 計測タスクにRedis、リードレプリカ、全面キャッシュを同時導入する。

#### 受入条件

1. 同じコマンドで再実行でき、テストデータ量、アプリ設定、DB仕様が記録される。
2. 各段階のp50/p95/p99、スループット、エラー内訳がある。
3. DBプール待ちとSQL実行時間を区別できる。
4. 上位5つの遅い/高頻度APIと、そのSQL本数が示される。
5. 推奨変更ごとに「期待効果」「副作用」「再計測方法」が記載される。
6. アプリの業務コードは変更しない。観測用の変更が必要な場合は最小限とし、公開範囲と認可を説明する。

### 4.3 C0後の判断木

| 実測結果 / 要件 | 次の対応 |
|---|---|
| 特定の読取APIが同じ集計を反復 | C1: そのAPIだけ短TTLキャッシュまたは集計クエリ化。キーにデータスコープを含め、冷キャッシュは `sync=true` 相当でスタンピードを防止 |
| 一覧APIのSQL本数がデータ件数に比例 | C1: N+1をバッチ化。必要列だけ取得し、ページング前提を維持 |
| Hikari pendingが増えるがDB CPUは低い | 長いトランザクション、接続保持、外部I/O混在を調査。プール増加は原因確認後 |
| DB CPU/IOが飽和 | SQL/索引/読取量を先に削減。リードレプリカは読取整合性要件を確認してからC3として設計 |
| 複数インスタンスまたは無停止更新が必須 | C2: Spring Session Redisを導入し、セッション共有・TTL・障害時挙動を設計。スティッキーセッションだけを恒久策にしない |
| 単一インスタンスで要件達成 | Redis/リードレプリカは導入しない。運用監視と容量限界を文書化する |

### 4.4 C1〜C3の設計境界

#### C1: クエリ削減・限定キャッシュ

- 実測で上位に出たAPIだけを対象とする。
- キャッシュキーには認証者のデータスコープを含める。
- 個人情報をユーザー間で共有するキー設計を禁止する。
- 更新時の厳密なevictか、業務上許容できる短TTLを明示する。
- 変更前後を同一負荷条件で再計測し、改善しなければ採用しない。

#### C2: セッション外部化

- 複数インスタンス/ローリング更新が必要な場合だけ実施する。
- 推奨はSpring Session Redis。アプリDBへセッション負荷を追加するSpring Session JDBCは、Redisを運用できない制約がある場合の次善策とする。
- ログイン、CSRF、Remember-Me、freee OAuth state、セッション失効、Redis停止時の挙動を統合テストする。
- セッションへ格納されるオブジェクトのシリアライズ互換性を確認する。

#### C3: リードレプリカ

- SQL/索引/キャッシュ後もDB読取が飽和し、レプリケーション遅延を許容できる読取だけが対象。
- 更新直後の詳細表示、締め処理、請求/入金、認可判定を安易にレプリカへ流さない。
- トランザクションのreadOnly判定だけに依存せず、対象サービスと整合性要件を明示する。

### 4.6 レビュー観点

- 「ユーザー数」だけでなく、同時アクティブ数とreq/sが記録されているか。
- H2ではなくMySQLで、warm/cold条件とデータ量が固定されているか。
- CSRF失敗やログイン画面へのリダイレクトを成功レスポンスとして数えていないか。
- p95悪化をSQL時間とプール待ちに分解しているか。
- 負荷発生器自体がボトルネックになっていないか。
- キャッシュ候補にデータスコープ漏洩リスクがないか。
- Redisやレプリカ導入が要件ではなく好みで提案されていないか。

## 5. 作業の渡し方とレビュー手順

他AIにはTask A、Task B、Task C0を**別々に**渡し、同一コミットへ混ぜない。推奨順は次のとおり。

1. Task Bを実装、テスト結果と差分を提出させる。
2. 本文書のTask B受入条件に対してレビューする。未達があれば同じAIへ局所修正を返す。
3. Task Aを実装し、デスクトップ/モバイルの実描画をレビューする。
4. Task C0はコード差分より計測の再現性と根拠を先にレビューする。
5. C1/C2/C3はC0の結果と実運用要件が揃うまで着手しない。

AIから最低限受け取る報告は以下とする。

- 変更ファイル一覧
- 各変更がどの受入条件に対応するか
- 実行したテストと結果
- 手動確認の環境と結果
- 未検証事項
- 既知のトレードオフ

「全テスト成功」だけでは合格にしない。Task Aは実描画、Task Bは生成物の再読込とバッチ境界、Task C0は同一条件での再現性をそれぞれ必須とする。
