## 変更内容

- actor と request の tenant が一致し、既知のロールで tenant が存在することを必須とした。null tenant と未知ロールは拒否する。
- 案件・タスク・イベント・依存関係を tenant 条件付きで検索し、要員も同じ tenant で照合する。営業の閲覧・編集は現担当だけに限定し、過去の起票者であることを権限根拠にしない。
- タスク一覧と案件詳細では、非表示タスクの名称・コード・イベントを投影しない。非表示の前提タスクは準備状態の判定にだけ使い、ブロック理由に名前やコードを含めない。
- COMPLETED / WAIVED / CANCELLED のタスク開始を拒否し、完了済みタスクの冪等応答より前に tenant と権限を検査する。
- lifecycle template の作成・改定・有効状態変更を service と API の両方で管理者/HR に制限した。
- tenant 別の最大番号検索を保ちながら全体一意制約を維持するため、案件番号に tenant ID の SHA-256 短縮キーを含める。生の tenant ID は案件番号へ露出しない。

## P2 追加修正（指摘: 案件番号競合・actor無効化）

- `case_no` 採番を tenant・年月単位の `t_lifecycle_case_sequence` 行に集約し、MySQL の `INSERT ... ON DUPLICATE KEY UPDATE` と条件付き `UPDATE` で初期値の復元と連番確保を原子的に行う。プロセス内ロックには依存しない。既存の同一 tenant/月案件番号から最大数値suffixを復元するため、9999 の後も 10000、10001 と継続する。tenant識別子は番号に生値で含めず SHA-256 先頭96bitを用いる。VARCHAR(50) に収まらない番号は409で明示的に拒否し、切り詰めや折返しはしない。
- V183 を追加し、H2 の test schema にも同じ表を追加した。既存案件番号の UNIQUE 制約は維持している。
- `LifecycleScopeService.requireTenant` で actor を毎回 DB から再読込し、status=1、role、tenant一致を要求する。無効/削除済み/不在 actor は詳細・開始・完了再送・waive・案件変更の認可より前に拒否する。無効actor経由では状態・イベントが変更されないことをテストした。
