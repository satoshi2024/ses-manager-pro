## 1. 実装済みの事実と不足

`LifecycleTaskServiceImpl.completeTask(Long, Long, CompleteLifecycleTaskCommand)`はtransaction内でactorを`requireActor`し、`LifecycleScopeService.requireTenant`を通してtenantを確定し、`LifecycleTaskMapper.selectByIdForUpdateAndTenant`でtaskをロックする。caseとengineerをtenant付きで読み、`LifecycleScopeService.assertCanEditTask`、case状態、task状態、先行taskを検証する。成功時はtask、`LifecycleEvent`、後続task昇格を更新する。caseは通常の`selectByIdAndTenant`であり、complete経路ではcase行をロックしていない。taskは`@Version`を持ち、mapperの`FOR UPDATE`も使う。

同メソッドの`DOCUMENT_LINK`判定は必須taskで`documentId`の有無だけを検査する。任意taskではdocumentなしでも進める。documentが渡された場合は`documentMapper.selectById`で存在だけを確認し、`documentVersionId`、tenant、ACL、version所属、scan状態、hash、storage状態、hold/disposalをこの経路では検証しない。その後`LifecycleEvidenceLink`にtask/document/version ID、時刻、actor、remarksを書き、taskを完了させる。`LifecycleEvidenceLink`にはtenant、generation、revision、hash列がない。

`LifecycleTask`には`evidenceType`（`NONE`, `SELF_DECLARATION`, `DUAL_CONFIRMATION`, `DOCUMENT_LINK`, `SYSTEM_CHECK`）と楽観`version`があるが、`task_generation`もcurrent submission pointerもない。`completeTask`は`DUAL_CONFIRMATION`を特別扱いせず、現行のrole/scopeを満たした単一actorでtaskを完了できる。二段階submission/confirmation APIや永続化表は確認できない。

`LifecycleApiController.completeTask`と`MyLifecycleApiController.completeTask`はSecurityContext由来のuser IDで同じserviceを呼ぶ。service内の`requireTenant`はDBの`sys_user`を再読込してactive/status、role、tenantをSecurityContextのuser情報と比較する。一方、`LifecycleScopeService`のscope判定はrole別に`OrganizationScopeService`, `EngineerSalesService`, `EngineerAccountLinkService`を呼ぶ。現行のrole判定はpermission-group actionを直接評価しない。menu permission（`t_role_menu`）はcase単位のscope認可ではない。

文書側の実装点は`DocumentServiceImpl.assertDocumentAccessAllowed(Document)`、`DocumentVersionMapper.findByTenantAndDocumentId(tenantId, documentId)`、`FileScopeValidationService.assertDownloadAllowed(storedName, expectedDocumentVersionId, expectedHash)`である。後者のexact version/hash引数は現行実装全体で一般文書の版を常に検証する契約ではなく、`CERTIFICATION_EVIDENCE`等の専用経路に結び付いた検証もある。lifecycle facadeから呼ぶだけで一般文書のexact検証を満たすとは扱わず、汎用文書用にID/tenant/document/hash/scan/storageを一貫して検証するservice/query境界を新設または拡張する。`DocumentApiController.download`と`FileApiController`のrouteも独自にfile-scope検査を行う。文書台帳serviceの存在だけをroute横断のACL保証とみなさない。`DocumentVersion`はtenant/document/versionNo/storageKey/sha256/scanStatusを持ち、entityコメント上append-onlyだが、lifecycleから厳密な`id + tenant + document`版取得を行うqueryは現状確認できない。

## 2. 目標契約

新しい提出・確認の業務判断はtransactional serviceに集約する。controllerは認証principalからactorを渡し、bodyで受けたactor、tenant、role、decision、hash、storage keyを認可根拠にしない。提出者と確認者はそれぞれ現時点の`sys_user`行からtenant、status、roleを確定し、両者とも同じ対象case/task/engineerに対する現在scopeを明示評価する。確認者は提出者と別の有効ユーザーで、roleは`管理者`または`HR`に限定する。manager、disabled/deleted user、tenant不一致、scope不一致、認可依存先の不明・timeoutは拒否する。提出時scopeだけで確認を許可せず、確認時に提出者と確認者の双方を再評価する。

権限モデルは現行のrole/menu/data-scopeと`LifecycleScopeService`のrole別規則を再利用し、このsliceで新しいpermission-group action gateは追加しない。menu/APIアクセスは現行SecurityConfigとMenuPermissionFilter、case/task scopeは現行LifecycleScopeServiceの述語に従う。明示actorの評価はactorのDB行を直接渡し、submitterの組織scopeをconfirmation actorのSecurityContextから計算しない。現行`OrganizationScopeService`はSecurityUtils/request cacheに依存するため、submitterを評価するときは同じ既存規則を`tenant_id + user_id + valid date`条件のDB読取で解決する。managerは`t_user_organization`のactive primary assignmentと`m_organization_unit`階層、salesは`t_engineer_sales`の`released_at IS NULL`、engineerは`t_engineer_account_link`、task actorは`t_lifecycle_task.assignee_user_id/assignee_role/is_engineer_visible`を照合する。HR/adminの現行規則はtenant一致後にcase/task全体を許可する。新たなrole/action semanticsは持ち込まない。

認可の世代は`(globalAuthorizationEpoch, tenantAuthorizationEpoch, submitterActorEpoch)`のtupleとする。全tenantに効くrole→menuやglobal config変更はglobal epoch、tenant内DataScope/OrganizationScope/AssetScopeのいずれかを変えるsource mutationはtenant epoch、`sys_user` active/status/role/tenant/deletedまたは既存PRIVATE_NOTE action assignment変更はactor epochを同txで進める。submissionはこのtupleとdocument eligibility epochをsnapshotする。confirmationはglobal/tenant epochとsubmitter actor epochがsubmission値に一致し、confirmerのcurrent actor epochと既存述語が有効なときだけ通す。grant後もepochを巻き戻さず旧submissionを復活させない。

このPLANの次実装は基礎sliceに限定する。`t_authorization_global_epoch`, `t_authorization_tenant_epoch`, `t_actor_authorization_epoch`とdocument eligibility epochを先に導入し、immutable submission/confirmation/event記録、canonical request/evidence hash、内部lock-plan retryを実装する。証跡候補をdocumentType=`SKILL_SHEET`かつ単一`ENGINEER` linkに限定し、起点writerを`EngineerChangeRequestServiceImpl.confirmSkillSheet`→`DocumentServiceImpl.registerGenerated/link`→`DocumentMetadataCommitService.commitNew`に閉じる。他のdocument target/typeはfail-closedにする。公開confirmation routeはこのsliceでは作らず、既存`completeTask`から`DUAL_CONFIRMATION`を完了できないようにして二者確認を閉じる。全document ACL predicateと全attachment writerの閉包、confirmの2-session MySQL証明が別途Astra reviewを通るまで、CONFIRMを有効化せず本機能全体の完了を宣言しない。

## 3. 証跡文書の共通解決

狭いlifecycle evidence facade（新規service案。具体名とAPIは実装時に既存service境界を確認して決定）を提出時・確認時双方で使う。`DOCUMENT_LINK`だけでなく、文書添付を含む`DUAL_CONFIRMATION`、複数添付、将来の文書証跡を含む全evidence typeが同じfacadeを通る。evidence type別の認可迂回を認めない。

clientが選択した`documentId`と`t_document_version.id`は入力として受け取れるが、版番号`versionNo`とは区別する。client hash、storageKey、title、scan statusは根拠にしない。facadeは認証tenantで文書を特定し、現在のdocument ACL/target scopeを検証し、指定versionが同じtenant/documentに属することを検証する。最新版への暗黙fallbackはしない。versionなしの`DOCUMENT_LINK`はmandatory設定に関わらず証跡として拒否する（任意taskで証跡なし完了を認める要件があれば、証跡省略の可否とtype semanticsを別途明文化する）。

提出と確認の双方で、文書が利用可能な状態か、exact `DocumentVersion.scanStatus == CLEAN`か、`DocumentStorage.open(storageKey)`が成功しSHA-256内容が版metadataと一致するか、documentが`DISPOSED`でなくlegal hold/disposal requestで利用不可かを再評価する。Document Archiveでは`t_document_version.scan_status`を唯一のscan authorityとし、`FileSecurityMetadata.storageState/scanStatus`は別の`FileStorageServiceImpl` file familyに限定して判定へ混ぜない。新設/拡張する汎用文書検証境界でexact document version ID/hash、storage参照と実体を検査する。現在の`FileScopeValidationService` overloadは特定file typeの検査を含むため、それを一般evidenceの保証と誤認しない。DBから確定したtenant/document/version ID/versionNo/SHA-256/eligibility epochをcanonical evidenceへ格納する。提出後に最新versionが増えても保存済みevidenceは切り替わらない。確認時にACLが撤回されepochが進んでいれば確認できない。

文書名、storage path/key、別tenant/非scope文書のmetadataをAPI responseやエラーから漏らさない。提出時と確認時の文書詳細/ダウンロードもその時点のACLを再評価する。download controllerの既存認可をfacadeの代用にしない。

## 4. DUAL_CONFIRMATIONの状態・冪等性・不変証跡

`DUAL_CONFIRMATION`の最初の操作はsubmission作成で、taskは`IN_PROGRESS`のままとする。confirmationは異なるactive actorによる別API操作であり、HTTP再送、同一idempotency key再送、画面の自己申告を二人目の確認として扱わない。既存`completeTask`は`DUAL_CONFIRMATION`を拒否し、非DUALの従来動作は互換対象として維持する。通常証跡を含む非DUALの文書証跡も新facadeを経由させる。

routeは既存`/api/lifecycle`と本人向け`/api/my/lifecycle`の公開面を確認したうえで決める。既存controller双方から同じserviceへ委譲するか、片方に集約するかはimplementation reviewで固定する。新API bodyに許すのは楽観version、idempotency key、業務コメントと証跡入力など必要な値に限る。actor/tenant/role/confirmation outcome/hashは入力拒否し、無視して受け付けない。confirmation actorはSecurityContextから取得する。

immutable submissionには少なくともtenant、case、engineer、task、task generation、submission revision、submitter ID/role/`globalAuthorizationEpoch`/`tenantAuthorizationEpoch`/`actorAuthorizationEpoch` snapshot/time、expected task version、evidence type、canonical evidence JSON/hash、文書版ID/版番号/hash/`evidenceEligibilityEpoch`群、idempotency key、server-computed request hashを保存する。confirmationも追記専用行とし、tenant/case/engineer/task/generation/submission/revision/evidence hash/confirmer ID/role/current `globalAuthorizationEpoch`/`tenantAuthorizationEpoch`/`actorAuthorizationEpoch` snapshot/time/decision/idempotency key/request hashを記録する。拒否・失効理由は既存行の上書きではなくappend-only eventで記録する。

canonical evidence JSONは固定schema、UTF-8、固定key順、null/空値/日時/数値の正規表現を定義してserver生成する。複数添付の順序は明示sort keyまたは正規化したdocument ID順に固定する。同一意味payloadのcanonical hashをSHA-256で計算する。idempotency unique keyは`(tenant_id, task_id, task_generation, operation, actor_user_id, idempotency_key)`。`operation`は少なくともSUBMIT/CONFIRMを区別する。request hashはstableなclient document/version selectionと業務上意味あるbody値（コメント等）から計算し、serverが初回処理で割り当てるsubmission revisionやDB生成IDを含めない。confirmationのsemantic requestは`submission_id + submission_revision + canonical_evidence_sha256`に結合する。同一key/same hash retryはsubmitter/confirmerのcurrent authと全document epochを再確認してから既存結果を返す。same key/different hashは409。old generationのretryは現generationに紐づかないため409。同一key/同一結果のterminal retryであっても双方のcurrent authとdocument epochを再検証し、認可失効後やepoch mismatch後に成功結果を返さない。

## 5. generation/current selectionと永続化

一generationにつき確認対象のcurrent submissionは最大一つとする。新submissionを受理するとき同一transactionでtask/current projectionを直列化し、旧pending submissionの失効event、新revision submission、current pointer更新を一括commitする。lifecycle自身のhold/cancel/reassign等、対象taskの担当・実行可能性を変える遷移はtask generationを増やして古いsubmissionを確認不能にする。resume後は新generationで新規提出を要求する。過去submission/confirmationはimmutable historyとして残す。

文書利用可否はtask generationと独立した`t_document.evidence_eligibility_epoch`（`BIGINT`, monotonic）でfenceする。submissionは各documentのepochをsnapshotに保存する。confirmationはdocument rowを再ロックしepoch一致を要求する。不一致は409/再提出要求とし、旧submissionを別versionへ差し替えない。epochを進める条件はlegal hold開始、`t_document_link`のtarget解除/削除、文書を確認不可にする処分開始、既存versionを利用不可にするscan状態変更である。release/regrant/scan再cleanはepochを戻さず、失効submissionは新規submissionを必要とする。版追加だけではepochを進めない。固定済み旧versionが現時点でもCLEANで利用可能なら、new latest versionが増えても既存submissionを有効なまま確認できる。

現行`LifecycleTask.version`と`LifecycleCase.version`は既存の楽観versionであり、generationとは別の概念である。taskにはgeneration/current pointerがなく、review-current projectionも存在しない。新migration案はtaskのgeneration/current pointerとcurrent review projection、immutable submission、immutable confirmation、append-only eventを追加する。全lifecycle表でtenantを保ち、tenant/task/generation/revisionをDB unique/FKで拘束する。循環FKを避けるためnullable task pointerと作成順を設計する。DBがcanonical JSON/hash内容そのものを正当化するわけではないため、server canonicalizerとtransaction内検証を併用する。

FK/uniqueの実列とMySQL制約可能性をDDL作成時に決める。confirmationとsubmission間はtenant/task/generation/revision/hash一致をDB制約で担保できる形を優先する。current projectionのCAS versionとtaskのoptimistic versionの双方で更新競合を検出する。`evidence_eligibility_epoch`は既存`t_document`行に独立列として置き、document row自身を空リンク/空disposal集合にも効くstable serialization anchorとする。V1や既存migrationは編集せず新migrationとH2/test schemaを追随させる。V185は使わない。

## 6. transaction、lock順、認可撤回の線形化

以下を実装時の依存行と直列化契約とする。これは現在の全writerが満たすという説明ではない。すべて同一DB transactionで取得し、同種の複数actor・複数documentはID昇順にlockする。

全read/write入口で次の単一lock契約を使う。操作開始時にREAD COMMITTEDの新transactionを開き、まず非locking discovery readだけでtenant、case/task、submitter/confirmer、ACL linkとtyped target、scope根拠行、document/version/disposal requestの全IDを列挙する。tenant不明、必要なroot epoch未provisioned、tenantを安全に確定できないwriteはfail-closedとする。lock順は (1) global authorization epoch、(2) tenant authorization epoch、(3)関係する`sys_user`とactor epochをuser ID順、(4) case→task、(5) typed business/scope parentを固定rank・ID順（organization hierarchy→ENGINEER→customer→contract→proposal→project→sales activity→asset→asset assignment→acceptance/service request）、(6) document、(7) version、(8) document link/disposal child。`ENGINEER`はtyped targetとscope根拠で同じ`t_engineer`行を一度だけlockする。AssetAssignmentの実writer順を守りassetをassignmentより前に置く。readerはglobal/tenant/actor epochを`SELECT ... FOR SHARE`、関連source writerはglobal rootを`FOR SHARE`、tenant rootを先行`FOR UPDATE`し、global-scope writerはglobal rootを先行`FOR UPDATE`する。既存rootをsharedで取った後にexclusiveへupgradeしない。case/task・parent・documentはその後同じ順でlocking current readする。最後に同じtransactionのREAD COMMITTED locking current readでdiscovery時のtenant、全ID集合、epochと全認可predicateを再照合する。通常のRR snapshot SELECTを最終認可readに使わない。discovery集合/parent/tenantが変わっていたら不足分を途中でlockせず全transactionをrollbackし、新transactionで完全discoveryから最大3回再試行、なお不一致なら409 fail-closedとする。document-only writerはdocument以下だけをlockしcase/taskへ逆行しない。

## 7. 基礎slice acceptanceとCONFIRM解放gate

基礎sliceで実装・検証する範囲は、global/tenant/actor/document epoch、immutable persistenceとcanonical hash、内部lock-plan retry、および`SKILL_SHEET`/`ENGINEER`の閉じた証跡writer pathに限る。

- Epoch fence: global epochは`RoleMenuApiController.update`→`RoleMenuServiceImpl.replaceMenus`と`SystemConfigApiController.update`→`SystemConfigServiceImpl.updateAll`の変更と同txで進む。tenant epochはscope predicateを変更する各writerと同txで進み、とくに`t_contract.sales_user_id NULL→B`でtenant内全sales submissionが失効する。actor epochはuser status/role/tenant/deletedと`PermissionGroupManagementServiceImpl.replaceAssignments`の変更と同txで進む。いずれもregrantで過去値に戻らない。
- Current reads/lock plan: transaction isolationはREAD COMMITTED。epoch rootはreaderが`FOR SHARE`、writerが最初に`FOR UPDATE`し、普通SELECTのRR snapshotを最後の認可readに使わない。barrier付き2-session MySQL testでglobal epoch、tenant `NULL→owner`、ENGINEER document unlink対confirmation判定の両順を確かめ、S→X upgradeなし、dependency discovery変化時は全rollback・新transactionから最大3 retryを確認する。
- Controlled document path: `SKILL_SHEET`かつtenant内単一`ENGINEER` parentのみ許可し、`EngineerChangeRequestServiceImpl.confirmSkillSheet`、`DocumentServiceImpl.registerGenerated/link`、`DocumentMetadataCommitService.commitNew`および`DocumentLinkMapper.updateById`のskillSheetConfirmedAt/Version更新まで一つの全順序へ移す。exact version/hash/CLEAN/storageとdocument epochを用い、unlink後のrelinkや新version追加の規則を確認する。別doc type、別target、未列挙writerはfail-closed。
- DUAL confirmation remains disabled: 公開submission/confirmation routeを追加せず、`LifecycleTaskServiceImpl.completeTask`相当の既存completion経路は`DUAL_CONFIRMATION`を拒否する。基礎sliceは二者確認完了を提供しない。

CONFIRMを有効化する前に、全対象document type/typed targetのpredicate・writerを同matrixで閉じ、unsupportedをなくすか個別に明示的な非対応要件として承認し、submitter/confirmer双方のcurrent scope/authorization、terminal retry、二confirm競合、document hold/disposal/scan、全writerとの2-session MySQL barrierを別レビューでPASSさせる。基礎sliceのPASSはこのgateを通過したことを意味しない。
## 8. 後続NF01→NF09 durable revoke request（本slice外）

後続batchでACTIVE RESIGNATIONからHR/adminが明示開始するtenant-scoped durable request/outboxを設計する。短いDB transactionでcase/engineer/account generationとstable idempotency key、actorを保存し、commit後workerがproviderを呼ぶ。provider I/Oを`LifecycleCaseServiceImpl.completeCase`のtransaction/lock中に実行しない。NF09現行`requestRevokeWithIdempotency`は`NOT_SUPPORTED`でclaim後providerへ同期送信し、claim後・送信前crash時に同key再送では再送しないため、durable dispatcherとsend-stateが別途必要。送信後ACK前crashはprovider idempotency/status-query契約が無ければUNKNOWNのままblockする。本sliceの文書ACL/DUAL完了をNF09統合や退社完了の証明として扱わない。

### 9.1 現在のschemaと確定した欠落

現在の主キーは各台帳で`BIGINT AUTO_INCREMENT`である。`sys_user.tenant_id`と`t_lifecycle_case.tenant_id`はV163で追加され、どちらも`VARCHAR(100) NOT NULL DEFAULT 'default'`。`t_lifecycle_task`にはtenant列がなく、`case_id`でcaseに属する。`t_document`/`t_document_version`のtenant列と`(tenant_id,id)`一意indexはV1基準schemaにあり、`t_document_link.tenant_id`はV162で追加された。`t_document_disposal_request`には現在tenant列もdocument FKもなく、document IDで親へ遡る必要がある。`m_system_config`と`t_role_menu`はtenant列を持たないglobal dataである。schema factsは`V1__create_tables.sql`、`V162__nf02_nf03_boundary_repair.sql`、`V163__nf02_nf03_tenant_attachment_notification_boundary.sql`で確認した。

現在の`t_lifecycle_case`は`version`を持ち、`t_lifecycle_task`も`version`と`evidence_type`を持つが、task generation/current submission pointerはない。`t_lifecycle_evidence_link`は`task_id,document_id,document_version_id,verified_at,verified_by,remarks`だけで、tenant、hash、task generation、submission revisionを拘束しない。現在のepoch表、submission、confirmation、idempotency表も存在しない。`Document.version`は既存台帳の楽観CASに使われるため、eligibility世代と混同しない。

scope sourceのtenant境界にも差がある。`Engineer`/`Customer`/`Contract`/`SysUser`/`EngineerAccountLink`/`UserOrganization`/`LifecycleCase`はtenantを保持する一方、`Proposal`/`Project`/`SalesActivity`/`EngineerSales`/`OrganizationUnit`/`Asset`/`AssetAssignment`/`AssetLostIncident`のentityにはtenant fieldがない。これらをtenant writerとして扱う時は、proposal→engineer/customer、project→customer、sales activity→customer/creator、engineer-sales→engineerとsales user、organization→tenant付きmembership、asset→assignment対象のように現行の信頼可能な親関係から影響tenant集合を解決する。複数tenantにまたがる変更はtenant rootをtenant ID昇順にすべてlockする。親がNULL/不一致、集合を完全列挙できない、またはtenant rootが未provisionedなら更新を拒否する。暗黙の`default`補完や任意のactorをtenant所有者に選ばない。必要ならtenant列を追加するmigration案を別途示し、今回のplanで既存データを推測backfillしない。

永続表の関係は次の形を推奨する。submission headerには`id`, `tenant_id`, `case_id`, `task_id`, `task_generation`, `revision`, `submitter_user_id`, `submitter_role_snapshot`, global/tenant/submitter actor epoch、`expected_task_version`, `evidence_type`, canonical request/evidence JSONと各SHA-256、`created_at`を置く。uniqueは`(tenant_id,task_id,task_generation,revision)`と、current pointer/confirmationが参照できる`(tenant_id,task_id,task_generation,revision,id,evidence_sha256)`。FKは`(tenant_id,case_id)`→case、`(case_id,task_id)`→task、`(tenant_id,submitter_user_id)`→user。caseに`UNIQUE(tenant_id,id)`、taskに`UNIQUE(case_id,id)`、userに`UNIQUE(tenant_id,id)`を追加する。taskの現generationはFKでなくtask row CASで検査し、generationが進んでも旧submissionを保持する。

submission evidence子表には`tenant_id,submission_id,document_id,document_version_id,version_no,sha256,evidence_eligibility_epoch`を保持し、submissionへのFKとdocument/versionへのtenant付きFKを置く。版が別documentを指さないこともDBで拘束するため、`t_document_version`に`UNIQUE(tenant_id,document_id,id)`を設け、子表の`(tenant_id,document_id,document_version_id)`から参照する。submission headerへの参照は`(tenant_id,id)`一意keyを使う。confirmation表には`tenant_id,case_id,task_id,task_generation,submission_id,submission_revision,evidence_sha256,confirmer_user_id,confirmer_role_snapshot,global/tenant/confirmer actor epoch,decision,decided_at`を保存し、上記submission binding列一式からsubmissionの同列unique keyへFKを置く。同じsubmissionに対するterminal decisionは`UNIQUE(tenant_id,submission_id)`で一件に限定する。

current projectionは`tenant_id,case_id,task_id,task_generation,revision,submission_id,state,projection_version`を持つ一task一row（PK `(tenant_id,task_id)`）とし、tenant/case、case/taskへのFKとsubmissionへの複合FKを置く。projectionのgenerationがtaskのcurrent generationに一致することは同transaction内のtask current read/CASで検証する。revision pointerの更新だけがmutableで、初回submissionまではrowなし。idempotency表は`tenant_id,case_id,task_id,task_generation,operation,actor_user_id,idempotency_key,request_sha256,submission_id,confirmation_id,created_at`を持ち、unique `(tenant_id,task_id,task_generation,operation,actor_user_id,idempotency_key)`。keyは長さ1..190のUTF-8を許す場合、index列の文字set/collationを固定してMySQL InnoDBの最大index byte長を検証する。別tenantのcase/task/userを組み合わせられない複合FKを付け、既存のsoft-delete運用に合わせて新history表を親削除cascadeにしない。

append-only eventは`tenant_id,case_id,task_id,task_generation,submission_id,actor_user_id,event_type,reason_code,occurred_at`と必要最小のhash参照を持つ。失効・supersede理由や拒否は既存submissionを更新せずeventを追記する。権限不一致のdeny eventにdocument title/storage path等を複製しない。個人情報や業務commentをeventへ複製する場合は監査retention/privacy reviewを先に行う。

tenant epochのbackfillは`sys_user`だけをtenant registryとみなさず、既存のtenant-bearing user、lifecycle case、engineer/customer/contract、document/version/link、organization/account membership、scope sourceのtenant集合を列挙してdistinct seedする。tenant列が無いsource rowは既知parentから全件owner解決できることをpreflightし、NULL/ambiguous/親子tenant不一致はmigration停止条件とする。新tableは`tenant_id`照合のFK先が無いためepoch表自身をtenant存在の唯一の根拠にしない。actor epochは既存全`sys_user(tenant_id,id)`をseedする。document epochは全`t_document`へ0でbackfillし、disposal request tenant backfillは親documentとの一致確認後にだけNOT NULL/FK化する。

初期化時に旧`t_lifecycle_evidence_link`から過去submission/confirmationを捏造しない。既存taskはgeneration=0、current pointerなしとし、既に完了済みのDUAL taskを新confirmation記録済み扱いにしない。過去`DocumentVersion.scan_status`は現値を維持し、CLEANでない版をCLEANへ補修しない。H2のcurated schemaと`engineer-schema-h2.sql`にもDDL確定後に同じ表/列/index/FK前提を反映する。

### 9.2 epochを進めるwriterと直列化

epoch rowはpredicateを守るすべてのwriterに同一DB transactionで結び付ける。cache invalidationやafterCommit通知は永続fenceにならない。writerは古い状態をlocking readで読んだ後に変更し、同一transaction内でepochを一度増やす。変更がno-opなら増分しない。multi-row operationではroot epochを先に確保し、後からrootへ戻らない。

### 9.3 coordinatorのtransaction境界、retry、current read

controllerから呼ぶ`LifecycleEvidenceCoordinator`（仮称）はtransactionを保持しない。`Propagation.NEVER`相当でambient transactionがあれば拒否する。理由は既存transactionをsuspendしても取得済みrow lockは保持され、後続`REQUIRES_NEW`が同じ行を待って自分自身をblockするためである。orchestratorはdiscoveryとretryだけを行い、別Spring beanの`LifecycleEvidenceTransactionService`へ毎回新規`REQUIRES_NEW`, `READ_COMMITTED` attemptを委譲する。例外をtransaction proxy外へ出してrollback完了後にだけ再試行し、最大3 attemptでなおdependency setが異なる場合は409 fail-closed。self-invocationや同一transaction内の「足りないlock追加」は不可。

各attemptは、SecurityContextから得たprincipal IDを入力にDB上のactive `sys_user(id,tenant_id,role,status,deleted_flag)`を確認しtenantを決める。bodyのtenant/actor/role/hash/storage値は受け取らず、参照IDはすべて決定済みtenantでdiscoveryする。最初の非locking discoveryは全scope依存集合（空link/assignment membershipを含む）、exact document/version/disposal IDs、task generation/current pointer、両actor IDsを得る。`LifecycleLockPlan.from`でrank/partition/idを正規化し、順にglobal root、tenant root、`sys_user`/actor epoch（user ID昇順）、case、task、typed business parent（asset→assignmentの既存順を含む固定rank）、document、version、link/disposal childをlocking current readする。last stepでは同じtransaction内で再discoveryの集合を再構成し`requireSameDependencies`を呼ぶ。集合変化はrollback後のnew attemptへ戻し、最終predicateはREAD COMMITTED locking/current readsで確認する。普通のsnapshot SELECTを最後の権限根拠にしない。

submission transactionでは同じkeyのidempotency rowを読む前に現在のactor/scope/epochとdocument epochを検証する。同key/同hashのretryは、現在も両側の必要権限と提出documentが使える場合だけ既存submissionを返す。同key/異hash、generation mismatch、epoch mismatchは409。新revision、immutable submission/evidence、superseded event、current pointer CASを同transactionに記録する。task generationはsubmissionで増やさず、lifecycle state/assignment changeだけが増やす。confirmation transactionはsubmission/pointerを再読込し、submitterとconfirmerの各`sys_user` active state/tenant/current scopeを明示actor DB readで評価し、global/tenant/submitter epoch snapshot一致、confirmer actor epoch current、全document eligibility epoch一致を確認する。別人は同tenantかつHR/admin role、submitterと異なるIDを必須とする。成功confirmation/eventとtask CAS、pointer終端化は同transactionで行い、一意制約で2人以上の同時confirmationのうち1件だけterminal commitを許す。

ambient transaction境界のためconfirmation routeはtransactional serviceを直接呼び、controllerは前後にDB lockを取らない。既存`LifecycleTaskServiceImpl.completeTask`からDUALを拒否する既存guardは維持する。非DUAL taskの既存complete APIを新coordinatorへ一挙移行しない。新routeやsubmission UIはschema+epoch writerの未閉鎖期間中に外部利用可能にしない。

### 9.4 document eligibility、exact version、tenant拒否

evidence APIはdocument IDと`t_document_version.id`のみをclient selectionとして受け取り、versionNo/hash/storageKey/title/scan statusをclient authorityにしない。serverは`document_version.id + tenant_id + document_id`で同一親を検証し、DBから得た`version_no`, lowercase SHA-256, `scan_status`, `storage_key`でexact evidenceを組み立てる。latest-version fallbackは禁止する。`DocumentVersion.scan_status='CLEAN'`だけがDocument Archive scanの権威。`PENDING/REJECTED/SKIPPED`、unknown status、version row欠落、scanner/storage unavailable、`DocumentStorage.open`失敗、実byte SHA-256とmetadata不一致はいずれも提出・確認を拒否する。`FileSecurityMetadata`の`FileStorageServiceImpl`状態は同じfile familyではないため混ぜない。

同じtransactionでdocument rowから`tenant_id`, `status`, `deleted_flag`, `legal_hold_flag`, `evidence_eligibility_epoch`を確認し、全active tenant-scoped linkをcurrent readで解決する。一般documentは`DocumentServiceImpl.assertDocumentAccessAllowed`のcurrent predicateを保ち、各typed targetをactor DBから計算する既存role/data-scopeに結び付ける。`SKILL_SHEET`の最小対象は`ENGINEER`単一linkかつ同tenant engineerのみ。`SERVICE_REQUEST`等predicate/resolver未対応、linkなし、未知target、foreign tenant ID、document/link/parent間のtenant不一致はfail-closed。cross-tenant IDは文書名・title・storage keyを返さないgeneric 404とし、同tenantの明示scope拒否は403、stale generation/epoch/idempotency conflictは409。bodyのtenantやactor値でcross-tenant errorを回避しない。

holdは`legal_hold_flag`の変更ごとにdocument epochを増加させる。hold開始中は提出/確認を拒否し、解除時も前epochへ戻らない。disposal `PENDING`作成を直ちに不可用とし、`APPROVED`でも不可用を維持する。`REJECTED`や`FAILED`後に過去submissionを復活させず、新提出を要求する。`DISPOSED`またはdeleted document、epoch不一致は拒否する。新version登録はdocument lock配下で行うがeligibility epochは増やさず、既存exact versionが依然CLEANかつstorage/hash一致なら確認できる。scan authorityが後から撤回される機能を導入する場合、document→version CASとdocument epoch増分を同transactionに限定し、旧versionをCLEANへ戻すrescanを認めない。storage外部状態はDB epochでは線形化できないため毎回open/hashを検証し、失敗時はfail-closed。

### 9.5 実装順と独立してreviewできるbatch

各batchはV番号をrootが割り当てるまでDDLを作成しない。full confirmationは全tenant/actor/document writerが揃うまでcloseのままとする。

1. **epoch spine schema/preflight batch（最小の次batch）**: global/tenant/actor epoch表、`t_document.evidence_eligibility_epoch`、`t_lifecycle_task.task_generation`、document disposal tenant repairのschemaとpreflight/backfillを作る。global singleton・tenant union・全sys_user・全document/taskを0でseedし、欠落/孤児/親子tenant不一致でfailする。複合FK/unique/indexとH2/test schemaも同時に固める。immutable submission/current pointer/idempotency/confirmation表はcoordinator batchへ分離し、public submission/confirmation route・confirmation transactionはまだ作らず、epoch読取を認可に使わない。これで小さなschema shapeと安全な初期化を先にMySQL migration gateで独立reviewできる。
2. **global/actor root writer batch**: global menu/configとsys_user status/role/deleted、permission-group assignment、およびengineer-delete/resignationのdirect sys_user mutationをfenceする。tenant root seed/provision protocolも合わせる。writer root取得・actor row更新・epoch増分のMySQL lock testを通す。DataScope scope source writer群が閉じない限りsubmission routeを有効化しない。
3. **tenant scope writer batch**: §9.2のcontract/proposal/project/activity/engineer/sales link/organization/asset sourceをdomain群ごとに独立commitできるが、未実装domainを通る判断をdisabledにする。特に`NULL→sales_user_id`、empty membership/link、engineer-target重複lock、asset→assignment順をMySQL 2-session testする。
4. **document eligibility batch**: SKILL_SHEET/ENGINEER限定でall link grant/remove/soft-delete、hold、manual/retention disposal、exact version add、storage verificationを閉じる。`DocumentMetadataCommitService`の`REQUIRES_NEW`境界を守る。別type/targetをAPIとserviceの両方でdenyする。直接`DocumentLinkMapper.insert` writerが同対象を変更できる状態ではこのbatchをPASSにしない。
5. **coordinator schema/runtime batch**: immutable submission/evidence/confirmation/event、current projection/idempotency tableを追加してcoordinatorへ接続する。2-session MySQL barrierでsubmit/revoke、confirm/revoke、same-key retry、same-key/different-hash、two-confirm race、generation replacementを検証する。公開confirm routeはこのbatchと既存DUAL拒否テストがPASSしてからreview対象にする。

各batchは対応するMySQL migration ordering/locking gateとfast schema initialization gateを要求する。unit-onlyやH2-only成功ではMySQL row lock/READ COMMITTED順序を証明しない。production approval、人間運用の有効化、NF09 provider連携は別のapproval boundaryのままとする。

PLAN受理後に限りimplementation sliceへ進む。production承認、実環境有効化、独立した実在HR/admin利用者による二者確認は人間の責務であり、AI/実装者は代行しない。本書はPLANレビュー結果であり、実装PASS、migration適用、production承認を主張しない。
