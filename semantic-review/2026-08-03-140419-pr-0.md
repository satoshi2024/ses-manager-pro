# 承認ワークフローのラウンド・版管理・可視性対応

S07 Round 2では、承認申請をラウンド単位で再提出できるようにし、参加者・ルートスロット・対象データの版を管理する実装が追加された。4種類の対象にまたがる7つの更新経路へ版更新を組み込み、一覧SQL、委譲、口座情報のマスキング、月次締めの変更検知も拡張している。設計書の決定表と実装を照合すると、ラウンド遷移・terminal idempotency・競合再提出・slot quorum・delegation child authorityは概ね対応している。一方、承認適用時の版比較、既存申請の移行、権限キー、通知重複排除には、実運用で制御をすり抜ける経路が残る。

Watch for: **blocker / confirmed** 対象版の比較と承認適用が原子的でなく、競合更新後に古い申請を適用できる。**high / confirmed** V78が既存の進行中申請へ参加者を移行しないため、移行後に非管理者の申請が一覧から消える。**high / likely** 月次締めのfingerprintがプロセス内キャッシュに依存し、複数インスタンスでは変更検知が遅れる。

## High-level view

承認エンジンは対象の現在版を確認してからadapterの承認適用へ進むが、対象行のロックも期待版CASもその間を結んでいない。**blocker / confirmed** であり、版管理による古い申請の適用防止を競合時に満たさない。

V78の参加者テーブル作成に既存申請のbackfillがなく、**high / confirmed** で移行後の非管理者一覧から申請が消える。さらに、view/statusの交差条件には **medium / confirmed** の不整合があり、口座情報は設計・seedと異なる権限キーで判定される。

月次締めfingerprintはJVMローカルキャッシュ、reject/return通知dedupeはラウンド非依存である。前者には **high / likely** のマルチインスタンス整合性問題、後者には **medium / confirmed** の2回目通知欠落がある。

対象テストは成功したが、Docker不在でMySQLのfresh/legacy migration smokeは未実行である。**medium / confirmed** として、移行backfill、版比較の競合、権限キー、ラウンド別通知を実DBまたは回帰テストで確認できていない。

<summary>Issues (7)</summary>

1. **対象版確認と承認適用のTOCTOU** *(blocker / confirmed)* — 現在版の確認後に対象が更新されても、期待版条件なしで`applyApproved`が進む。対象更新を期待版CASまたは同一ロック範囲に含め、競合時は適用せずconflictへ遷移させる。
2. **V78の既存申請participant backfill欠落** *(high / confirmed)* — 参加者テーブルを作るだけで既存の進行中申請に行を作らないため、participantを要求する可視性SQLから非管理者の申請が消える。移行時の冪等なbackfill、または既存行を安全に扱う互換経路と実DBテストを追加する。
3. **view/statusの交差条件が置換される** *(medium / confirmed)* — `view=inbox&status=approved`や`view=completed&status=in_review`のような相互に矛盾する指定をSQLが排除しない。許可されたstatus集合との積を取るか、矛盾した指定を400で拒否する。
4. **口座情報の権限キー不一致** *(medium / confirmed)* — `canViewField()`が`bp-company.bank-account.view`を参照するが、設計・seedの権限キーは`bp-company.view`である。承認済みキーへ統一し、許可・不許可の両方をテストする。
5. **月次締めfingerprintのプロセス内キャッシュ** *(high / likely)* — 別インスタンスで締め設定が変わっても、承認処理インスタンスのキャッシュは更新されず古い申請を通し得る。DBの版/更新時刻を承認時に再確認するか、分散キャッシュ無効化を導入する。
6. **reject/return通知dedupeがラウンド非依存** *(medium / confirmed)* — round 1で使ったdedupe keyがround 2でも再利用されるため、再提出後のreject/return通知が一意制約で抑止される。keyにround/actionの発生単位を含め、2ラウンド分の通知を検証する。
7. **MySQL実行と重要経路の検証gap** *(medium / confirmed)* — Docker不在でFlywayのMySQL smokeがskipされ、競合・backfill・権限キー・ラウンド通知の回帰も未検証である。Docker利用可能なCIでfresh/legacy migrationを実行し、4経路の統合テストを追加する。

<summary>Details</summary>

### 対象版確認と承認適用のTOCTOU（blocker / confirmed）

`ApprovalEngineServiceImpl:200-215`は、`adapter.currentVersion(request)`で申請に記録された版と現在版を比較した後、対象行を期待版で更新する条件を持たない`adapter.applyApproved(request)`を呼ぶ。この間に別の更新が入ると、次の順序で古い申請が承認扱いのまま適用される。

```text
承認 A: currentVersion = v を読み、比較を通過
更新 B: 対象を v+1 に更新
承認 A: applyApproved(request) が期待版なしで対象を更新
```

4対象の7更新経路で版を増やしていても、承認側のread-check-apply間隔は埋まらない。`applyApproved`の更新SQLへ申請の期待版を含め、更新件数0をconflictとして扱うのが最小の修正になる。対象行を`SELECT ... FOR UPDATE`で保護する方式では、通常更新経路も同じロック規約を守る必要がある。

### V78の既存申請participant backfill欠落（high / confirmed）

`V78__approval_workflow_round_participant_version.sql:25-40`は`t_approval_participant`を作成するが、V78適用時点ですでに存在する申請から参加者行を生成しない。participantを権限の根拠にする可視性SQLのため、V78前に作成された進行中申請を非管理者がinboxやcompletedで取得できなくなる。新規DBでV75以降を順番に適用するだけでは検出できない。

移行時に既存申請のround・active step・slot・participantを再構成できるbackfillを、重複なく再実行できる形で追加する必要がある。完全な復元ができない場合は、旧申請だけを安全に可視化する互換条件を設け、legacy DBからのアップグレードテストで管理者・非管理者の双方を確認する。

### view/statusの交差条件が置換される（medium / confirmed）

`ApprovalRequestMapper:27-90`の一覧SQLは、`view`がinboxまたはcompletedのときに本来のview別status条件を持つが、明示的な`status`指定がその条件を置き換える。結果としてinboxに終端済みapprovedを、completedに進行中in_reviewを指定して取得できる。主体条件は別に残るため直ちに他ユーザーのデータを読む問題とは限らないが、画面のview境界とAPIの意味が一致しない。

`view`が定めるstatus集合と明示statusの積を空集合として返すか、組み合わせを入力エラーにするべきである。inbox/completedの許可・矛盾・未指定statusとページングを組み合わせたテストを追加する。

### 口座情報の権限キー不一致（medium / confirmed）

`ApprovalViewServiceImpl:72-77, 208-216`の口座・口座番号フィールド判定は`bp-company.bank-account.view`へ権限を解決する。しかし正本の設計・tasksとseed済みメニューは`bp-company.view`を承認済みキーとしているため、通常のBP権限を持つ利用者にも口座情報がマスクされる。これは漏えいではなく、許可された表示を拒否する側の不整合だが、承認画面の業務利用を阻害する。

設計どおり`bp-company.view`に統一するか、別権限を正式にseedしてロール設定と画面仕様を更新する必要がある。許可ロールではaccount/accountNumberが表示され、非許可ロールではマスクされることをサービス・ページ境界で固定する。

### 月次締めfingerprintのプロセス内キャッシュ（high / likely）

`MonthlyClosingApprovalAdapter:76-78, 110-113`は`SystemConfigService`から取得したfingerprintに依存し、`SystemConfigServiceImpl:25-26, 190-194`のキャッシュは`ConcurrentHashMap`によるJVMローカル状態である。after-commitの無効化も同じプロセス内に限られるため、複数インスタンスが同じDBを使う構成では、インスタンスAの承認がインスタンスBで行われた締め設定変更を検知できない可能性が高い。単一インスタンス運用を保証するならその制約を明記し、水平スケールを許すなら共有状態で再検証する必要がある。

承認時はキャッシュを経由せずDBの設定版または更新時刻を読み、申請時のfingerprintと比較するのが確実である。キャッシュを残す場合も、分散無効化と競合時の再読込みを組み合わせる。

### reject/return通知dedupeがラウンド非依存（medium / confirmed）

`ApprovalEngineServiceImpl:241-242, 268-269`のreject/return通知dedupe keyにroundが含まれていない。round 1で同じ申請に対する通知が作成された後、returnedからresubmitされたround 2で同じaction種別の通知を作ろうとしても、通知テーブルのglobal unique制約に衝突して抑止される。再提出は新ラウンドとして扱われるため、通知の重複抑止単位もroundを含める必要がある。

keyにrequest・round・action・recipientの発生単位を含め、同一round内の再実行だけを冪等にする。round 1とround 2のreject、return、再通知を分けて確認する回帰テストが必要である。

### 決定表と整合し、今回の追加修正を要しない範囲

round/participant/actionの一意制約、returned→resubmit→approve、terminal状態の冪等性、conflict後の再提出、step内any-ofかつ全step必須のslot quorum、委譲子テーブルを権威とする判定、`PageUtils.safePage`によるページ境界、4対象7経路の版更新は正本の決定表と整合している。申請者role条件はdesign §8の繰延として扱われており、この差分に対する追加修正は不要と判断する。なお、これらの保証は上記の承認適用TOCTOU、移行時backfill、通知dedupeの問題を解消するものではない。

### MySQL実行と重要経路の検証gap（medium / confirmed）

対象の承認・ルート・表示テストは37件がFailures 0、Errors 0、Skipped 0で、`MigrationScriptIntegrityTest`の26件も成功し、`git diff --check`も成功した。一方、`FlywayMigrationSmokeTest`はDocker daemonに接続できずskipされたため、MySQL上のfresh migrationとlegacy upgradeは未確認である。また、既存申請を含むV78適用、checkとapplyの同時実行、`bp-company.view`を持つ利用者の口座表示、round 2のreject/return通知を直接検証する回帰テストは確認できない。

Dockerを利用できるCIでFlyway smokeを必ず実行し、skipを許容しない運用を維持する。加えて、上記4経路をH2だけでなく、移行後データと同時更新を含む統合テストで固定する。
